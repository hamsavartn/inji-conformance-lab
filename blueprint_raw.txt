The baseline architecture's reliance on lightweight Node.js mocks fundamentally undermines this objective and severely jeopardizes the project's standing against the MOSIP Decode evaluation criteria, which allocates forty percent of the final score strictly to functional completion and complexity resolution1. Testing synthetic implementations against other synthetic implementations operates in a sterile vacuum, failing to expose the true behavior of the actual inji-certify Spring Boot backend, the mimoto Java backend serving as the wallet's Backend-for-Frontend (BFF), and the inji-verify Spring Boot service3. A playground that solely validates mock data guarantees a deduction in functionality scores by bypassing the precise networking constraints, database transactions, and cryptographic latency inherent to the native MOSIP Collab Sandbox2.To resolve this critical vulnerability, the system architecture demands a Hybrid Dual-Engine orchestration layer. This specialized middleware must operate as a dynamic reverse-proxy gateway. In a live configuration, the proxy transparently intercepts and forwards traffic directly to the MOSIP Collab Sandbox or local Dockerized Inji Stack components. This live connection acts as a cryptographic tap, capturing raw HTTP streams, header negotiations, and token exchange handoffs. Conversely, when deterministic offline testing is required, the engine seamlessly switches routing to high-speed, in-memory state machines. This dual-engine approach proves real-world native compliance while preserving the sub-100ms latency necessary for rapid user interface interactions, negative fuzzing, and continuous integration testing. By actively monitoring the API boundaries—specifically the Demonstrating Proof of Possession (DPoP) token exchange and the /credential endpoint in inji-certify—the system bridges the gap between simulated validation and actual enterprise readiness.Standards Compliance and Spec Drift PitfallsThe global digital identity ecosystem is highly fragmented across evolving protocol drafts, introducing severe risks of specification drift. The baseline project fails to account for the catastrophic breaking changes introduced between protocol iterations. The audit reveals critical vulnerabilities in standard compliance across four key dimensions, necessitating immediate architectural remediation.OpenID4VCI Draft Transition DynamicsThe current iteration of the Inji stack aligns heavily with OpenID4VCI Draft 133. However, the broader digital identity ecosystem—including the European Digital Identity (EUDI) framework, Walt.id, and Sphereon—is aggressively migrating toward Draft 14 and beyond5. The breaking changes between these drafts are not merely semantic; they alter foundational data structures. Draft 14 refactors the Credential Issuer metadata, officially deprecating the JSON array credentials_supported in favor of a JSON object defined as credential_configurations_supported8. Furthermore, the authorization_servers parameter transitioned into an array format to accommodate decentralized federations11.If an external wallet engineered for Draft 14 attempts to resolve metadata from inji-certify operating on Draft 13, the JSON parsing will fatally fault, blocking the issuance flow entirely. The Interoperability Playground must actively detect this schema drift. The proxy layer must implement an intelligent diffing engine capable of recognizing the metadata version, logging the exact structural mismatch, and optionally applying a translation layer to permit testing across divergent standard implementations.OpenID4VP Evolution and Query MechanismsThe inji-verify verification portal currently relies on OpenID4VP Drafts 21 through 2312. Within these specific draft versions, the response_mode parameter for cross-device authentication flows is strictly enforced as direct_post or direct_post.jwt14. While the payload format relies heavily on the DIF Presentation Exchange v2.0 for querying credentials, emerging wallet implementations operating on Draft 24 frameworks are mandating the Digital Credentials Query Language (DCQL) as the superior, highly optimized query format17. The architectural gap occurs when a verifier demands DCQL syntax, and an older wallet implementation cannot interpret the query structure. The playground must possess the diagnostic depth to highlight when a verifier requests an advanced OpenID4VP format that creates a deterministic failure for legacy wallets.IETF SD-JWT Cryptographic VulnerabilitiesSelective Disclosure JWTs (SD-JWT) introduce profound complexities regarding canonicalization and hashing faults. The architecture of an SD-JWT relies on a disclosures array (_sd) containing salted claims19. Any microscopic deviation in whitespace, array sorting logic, or base64url padding during the assembly of these claims completely invalidates the deterministic SHA-256 disclosure digests embedded within the issuer's token19.Furthermore, robust replay protection is entirely dependent on the strict validation of the Key Binding JWT (kb_jwt), which is appended to the conclusion of the SD-JWT credential payload and separated by a tilde (~) character21. This key binding must cryptographically prove possession by embedding the verifier's audience (aud) and the session nonce22. A baseline playground lacking forensic capabilities cannot visualize these discrete binding elements. An advanced cryptographic dissector is mandatory to deconstruct the token, separate the issuer signature from the holder binding, and independently verify the hashing logic of the _sd claims.ISO 18013-5 mDoc COSE/CBOR ComplianceThe implementation of mobile driving licenses (mDL) strictly dictates a binary format encoded in Concise Binary Object Representation (CBOR)24. This standard requires a MobileSecurityObject (MSO) to be securely wrapped within a COSE_Sign1 signature block25. These payloads are further encapsulated within CBOR Tag 24 (#6.24(bstr)) wrappers, ensuring byte preservation during transmission25. A generic JSON-based inspector interface is fundamentally incapable of processing or visualizing these binary structures. The laboratory environment requires a dedicated CBOR-to-JSON diagnostic bridge. This bridge must extract the MSO, verify the X.509 certificate chain embedded within the unprotected headers, and validate the specific driver privilege namespaces, such as org.iso.18013.5.125.SpecificationCore Vulnerability VectorRemediation StrategyOpenID4VCIcredentials_supported array vs. credential_configurations_supported object mismatch between Drafts 13 and 14.Implement a dynamic JSON schema diffing engine in the proxy layer to highlight structural deviations.OpenID4VPShift from DIF Presentation Exchange to DCQL in newer drafts.
